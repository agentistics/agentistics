# PERF — server CPU 40–130 % and event-loop stalls on the WSL machine (2.204.4)

Task t-8b8b437105 / subtask s-39a5049cde. Measurement only — no code changed.

## Sources of evidence
1. **The real server's own profiles.** `vigia-desempenho` (APP.LENTO) captured 10 × 10 s CPU profiles of the
   running `agentop server` (2.204.4 official, engine 0.1.0) on 2026-11-10, 03:51–13:59Z, each taken when
   CPU stayed > 25 % — `~/.agentistics/perf/*.cpuprofile` (copied to `/tmp/perf-cpu-alien/real/`). 109 s of
   samples, real data, real engine, real clients. Frames were mapped to source by extracting the bundle
   embedded in the binary (`/tmp/perf-cpu-alien/extract.ts`, `at.ts`; profile line N = bundle line N-1).
2. **Read-only probe of the real server** — `/api/version` once a second for 90 s (`probe.ts`).
3. **A throwaway reproduction** — community build from source, synthetic home (scale 0.2), under
   `agentop run --rm` + the heavy lock, own `AGENTISTICS_DIR`, free ports (`repro-which.ts`).

## Real server (read-only, 14:5xZ, ~12 local connections open)
- CPU 31–66 % (`top` 5 s samples; `ps` lifetime 65.9 %), RSS 0.95 GB, 108 min CPU in 2 h 44 min.
- `/api/version` (the event-loop probe), 90 samples: **p50 11 ms, p95 6 205 ms, max 22 899 ms**; 13 stalls
  > 500 ms (3.6, 4.1, 16.6, 20.3, 22.9, 17.7 s …). This is what made the 30 s `sessao-parada` flow call
  time out.
- The systemd unit's `Environment=PATH` carries 25 `/mnt/c/...` dirs (`systemctl --user cat agentop-server`).

## Reproduction (throwaway, community build, synthetic home)
| | CPU | `/api/version` p50 / p95 / max | `/api/vault` | `/api/accounts` |
|---|---|---|---|---|
| idle, no clients (60 s) | 3.1 % | 2 / 35 / 62 ms | — | — |
| one client: `/api/vault` every 15 s + `/api/accounts` every 60 s, PATH with `/mnt` | 2.1 % | 2 / **5 688 / 15 898 ms** | 11 858, 547, 3 868, 16 796 ms | 11 869, 17 157 ms |
| same, PATH without `/mnt` (control) | 2.5 % | 2 / 4 / 104 ms | 40, 6, 5, 9 ms | 494 ms |

The stalls are blocking I/O inside a synchronous call (9P lookups on `/mnt/c`), not CPU: CPU stays at
2 % while the loop is frozen for 16 s. So there are two different symptoms here:
- **"the server does not answer"** = `Bun.which` over `/mnt` (cause 1), proven by the control run;
- **"the CPU sits at 40–130 %"** = causes 2–6 (disk-index loop, task book parse, preferences clone,
  opencode, series), which run whether or not anyone is waiting.

Against 06/11 (APP.LENTO, real-data copy): loaded CPU then 42–48 % after the fixes, `/api/version` p95
45–126 ms; today on the real server p95 6.2 s. The regression is the vault poll (2.202.0) meeting WSL's
PATH, plus the always-on disk-index loop and the book growing to 15.8 MB.

## Limits
- Not re-run over a `copy-data.sh` copy of the real store with the engine linked: the real server's own
  profiles (engine loaded, real data) already cover that, and the throwaway reproduces the stall cause.
- Idle CPU of the REAL server (no clients) cannot be measured without closing the owner's tabs; the
  disk-index loop and its rebuild run without clients, so they are part of the idle figure.
- Shares are of the sampled time of profiles captured only while CPU was high (vigia's trigger), so they
  describe the hot spells, not an average hour.
