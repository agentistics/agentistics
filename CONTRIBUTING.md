# Contributing to agentistics

Thanks for your interest in contributing. This guide covers everything you need to get started.
Process rules (Issues, the Project board, Discussions) live in
[`AGENTS.md`](AGENTS.md) — read that first, this file is about the mechanics of building and
submitting a change.

## Development setup

**Prerequisites:** [Bun](https://bun.sh) v1.0+, Node.js is not required.

```bash
git clone https://github.com/blpsoares/agentistics.git
cd agentistics
bun install
bun run dev      # API on :47291, UI on :47292 (Vite proxies /api automatically)
```

> **Data source:** agentistics reads local files written by AI coding assistants (`~/.claude/`,
> `~/.codex/`, `~/.gemini/`, `~/.copilot/`, `~/.kimi-code/`) — you need at least one installed with
> some usage history for data to appear. See [`docs/data-sources.md`](docs/data-sources.md).

## Project structure

This is a Bun monorepo. Full detail (module-by-module) lives in `CLAUDE.md`; the short version:

```
packages/
  core/     (@agentistics/core)   — shared types, pricing, formatters, i18n
  server/   (@agentistics/server) — Bun HTTP server, the `agentop` CLI, otel-watcher
  web/      (@agentistics/web)    — React + Vite frontend (the dashboard)
  mcp/      (@agentistics/mcp)    — MCP server, publishable standalone
  tui/      (@agentistics/tui)    — Ink terminal control center (`agentop` front door)
  desktop/                        — Tauri v2 Windows installer
```

See [`docs/architecture.md`](docs/architecture.md) for how the pieces fit together, and
[`docs/harness-contract.md`](docs/harness-contract.md) before touching anything that computes a
metric across more than one harness.

## Running tests

```bash
bun run stub   # create a type stub if embedded-dist.generated.ts is missing
bun test
```

Tests cover pure functions only — `calcCost`, `getModelPrice`, `calcStreak`,
`getDateRangeFilter`, and others across `packages/*/src`. Do not mock the filesystem for these; if
a function needs mocking to test, it isn't pure enough to belong in the fast test suite.

> **Note on `embedded-dist.generated.ts`**: `packages/server/server/embedded-dist.generated.ts` is
> gitignored and generated by `bun run build:assets`. Without it, `bun tsc --noEmit` fails. `bun run
> stub` creates a minimal type-only stub so type checks and tests pass without a full build.

## Building the binary

```bash
bun run build:binary   # → release/agentop
```

This runs three steps: `vite build` (packages/web) → `build:assets` (embeds the dist into a TS
file) → `bun build --compile` (packages/server/bin/cli.ts). Verify TUI changes against the
**compiled binary**, not just `bun run cli` — some failures (e.g. the `react-devtools-core` stub)
only show up at compile time.

## UI / frontend contributions — mobile is not optional

**Any new screen, and any layout fix, ships its mobile version in the same PR.** This isn't a
follow-up task — a PR that only works at desktop width isn't finished. Concretely:

- Follow the existing conventions rather than inventing new ones: `useIsMobile()` (768px
  breakpoint), `MobileBottomNav` + its "More" sheet, full-screen modals/drawers on mobile, the
  `.ag-grid cols-N` utility, tables collapsing into card lists, popovers that flip up near the
  bottom of the viewport.
- **Touch targets ≥ 44px** on mobile (that number is mobile-only — applying it on desktop turns a
  segmented control into a row of oversized buttons).
- **Any `<input>` visible on mobile computes to ≥ 16px font-size**, or iOS Safari zooms the
  viewport and breaks the sticky header. Don't override the global guard in `index.css` with an
  inline `font-size`.
- **Verify at 390px width, don't assume it's fine**:
  `document.documentElement.scrollWidth <= window.innerWidth` must hold on every page. Wide tables
  and code blocks scroll inside their own container, never the page body.
- A new page's nav entry goes in **both** the desktop `SideNav` items array **and** the
  `MobileBottomNav` `navTiles` array — adding only one hides the page on the other form factor.

If you're unsure how an existing screen solved this, look at it before designing a new pattern —
consistency across screens matters more than a locally "cleaner" one-off.

## Commit convention

This project follows [Conventional Commits](https://www.conventionalcommits.org/):

```
feat: add per-project token breakdown
fix: sort heatmapData to prevent chart axis disorder
chore: update dependencies
docs: improve install instructions
```

Commit messages are in **English**.

**The type decides the published version.** `.github/workflows/release.yml` reads every commit in
the range and hands it to `bumpFromCommits` in `@agentistics/core` (`versionBump.ts`) — the one
tested implementation of the rule: a `!` or a `BREAKING CHANGE:` footer is a major, `feat` is a
minor, anything else is a patch. So a mistyped `chore:` over a real feature ships it as a
correction, and nobody reading the versions learns it landed.

Two rules exist because getting them wrong published v1.23.1 for a feature (#248):

- **Read git with `--pretty=tformat:`, never `format:`.** `format:` omits the terminal newline on
  the last record and `while read` drops it, so the OLDEST commit of the range goes unclassified.
  It is safe inside `$(…)`, which is exactly why the wrong form survives long enough to be copied
  into a loop. `releaseWorkflow.lint.test.ts` fails the build on either form.
- **The workflow never decides the bump itself.** `bumpFromCommits` throws when it is handed
  nothing to classify, so an unreadable range fails the job loudly. A bash `patch` default would
  turn that same failure back into a quietly wrong number.

## Submitting a PR

1. Fork the repo and create a branch from `dev` (ongoing work targets `dev`; `main` receives
   periodic releases cut from `dev` — see `AGENTS.md`).
2. Open or find the Issue the change addresses, and reference it in the PR (`Closes #N`) — a CI
   check enforces this; a genuinely trivial PR can carry the `no-issue-needed` label instead.
3. Make your changes — keep the scope focused. Ship the mobile version alongside any UI change
   (see above), and update `docs/*.md` in the same PR if the change affects behavior described
   there.
4. Run `bun test` to verify nothing broke.
5. Fill in the PR template for real: summary, motivation, and how you tested it.

## Architecture notes

- **Pricing calculations** live exclusively in `packages/core/src/types.ts` (`MODEL_PRICING`,
  `getModelPrice`, `calcCost`). Never inline cost math elsewhere.
- **`stats-cache.json`** is Claude-Code-only and has no project-level granularity — project/repo/
  non-Claude-harness aggregates are computed by summing individual sessions. See
  [`docs/metrics.md`](docs/metrics.md).
- **Binary mode** is activated by `SERVE_STATIC=1` (set by `agentop server`); in dev mode the
  embedded assets are never loaded.
- Full module-by-module documentation lives in `CLAUDE.md` (dense, written for an AI harness) and
  `docs/*.md` (the canonical, human-and-tool-readable version) — see the
  [wiki](https://github.com/blpsoares/agentistics/wiki) for an index.
